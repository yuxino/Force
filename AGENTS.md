# Force

Force is a local-first desktop calendar and timer built with Rust and GPUI. Keep all user data on the device; the app needs no account or server. Only an explicit update check contacts public GitHub Releases; never send local tasks, records or paths.

- `crates/force-core`: SQLite persistence, timer intervals, goals, history, CSV export and statistics. Keep it independent of GPUI and OS APIs.
- `crates/force-app`: native GPUI interface and platform integration. Support macOS, Windows and Linux without duplicating business logic.
- Force has two independent native windows: an 88 × 128-point floating cat clock (244 × 152 expanded, 28 × 80 edge-docked) and a normal, resizable management window, initially 1040 × 780 points with a 780 × 620 minimum. An idle cat opens a new task directly; clicking a prepared or active cat toggles its controls; dragging near the left or right screen edge docks it on macOS/Windows. Expansion is local UI state and must not change the timer or management visibility. Opening management leaves the clock in place; starting a timer preserves the user's current window visibility. Closing management preserves running timers and drafts. macOS and Windows hide it; Linux currently minimizes it and requires native acceptance.
- Keep three primary destinations: 日历 for scheduling and reviewing each day, 记录 for date-based detail, and 分析 for real interval trends and daily tables. Keep task/timer detail as a contextual destination, without a separate focus mode or navigation entry. Launch management on the calendar and preserve the independent floating clock. Settings is a secondary gear control. Put clock pinning in settings and CSV export only in records. The floating clock prioritizes the running timer even when management browses a paused task.
- Calendar combines scheduled occurrences and actual work in one month/day interface. Keep plans separate from recorded intervals, protect editor drafts, and show real task completions and sessions automatically; never label separate active/passive UI modes. A rescheduled occurrence retains its original-day marker. Point-in-time notes are separate from tasks and intervals: show them as time markers, never add them to focus duration.
- New tasks start in count-up mode with no activity preselected. Put the activity picker first; an optional description resolves to the activity name when blank. Show an existing title equal to its activity as an empty description, without rewriting it or creating false dirty state. Preserve distinct titles, saved countdown modes and suspended drafts. Do not turn an untouched count-up form into a prepared floating-clock task.
- The contextual task workspace keeps its Today summary and task navigation stable. Show real daily focus against its goal with one progress line. The summary stays outside scrolling content. Below it, only the left operation area changes between setup, running and completion; the right 240-point task sidebar remains available across states. Use one task list, including unfinished legacy sessions. Keep a single 新任务 action in the header on every page; it and Cmd/Ctrl+N open the task form without a schedule and return focus to the same draft when one is already being prepared. Preserve a suspended calendar draft when opening a task. Clicking a task selects it without starting or resuming it.
- Records start with a real-data activity calendar: 53 Monday-to-Sunday weeks, seven rows, neutral gray intensity, date/duration tooltips and day selection linked to the records below. Future dates are disabled. Load merged daily focus with one batch query, cache the series, and update today from the normal timer tick; never issue one query per cell or invent data.
- Follow `docs/plans/interface-consistency.md`: maximum content width 896 points, 68-point header, 32-point column gap, and settings using the full content grid: at window widths of at least 920 points, a 280-point timing/application column and a flexible tag column; narrower windows stack timing, tags and application sections. Use black, white and neutral gray, readable labels and short contextual help. Keep required actions and errors visible. Reuse `view.rs` helpers and `control_style.rs`; focus, records and settings rendering live in their own `*_view.rs` modules. The geometric wordmark and navigation share the content grid; task headings and full time readouts are left-aligned. See `docs/plans/workbench-redesign.md` for the current composition. Disabled start text is `#626262` on `#e9e9e9`; do not fade entire controls with opacity.
- Keep interface copy brief. Avoid repeating an action or state already clear from its label, timing range or nearby control; retain errors, countdown/elapsed meaning and distinctions such as ending a round versus completing a task.
- Classification colors are managed once in settings. Tags inherit their classification color unless explicitly overridden; use the shared live-color resolver on every surface, falling back to archived metadata only for deleted tags. Historical classification/accounting remains unchanged by display-color edits.
- History corrections and backfills are explicit actions. Preserve interval identities and paused gaps, reject edits to unfinished rounds, and compare a saved baseline before writing. Metadata-only edits retain exact timestamps. A backfill creates completed work at the chosen past time without affecting running timers. Keep record and task completion linkage consistent; preserve independently marked completion times.
- Active sessions survive restart. Use absolute timestamps, not tick counts. Pauses exclude time; computer sleep does not implicitly pause. Sum parallel task investment separately from merged focus time.
- Write changes transactionally. Preserve user data on errors. Never recover a damaged database by overwriting it with a blank one.
- Test with a dedicated temporary data directory. Do not read or modify a real user's records during acceptance.
- macOS previews must be signed with an existing private-key-backed identity. Use a separate Force Dev bundle and app data directory for previews. The user has made formal-app replacement a standing Force delivery requirement: after fixes or optimizations are complete and verified, replace the local formal app, preserving its signing identity, bundle identity, install path and user data. Verify the installed artifact and launch; a development bundle alone does not complete delivery.
- Layout regressions must measure the actual task title and status inside the button, not only the outer row. GPUI button content wrappers can shrink auto-width descendants even when the button fills its sidebar. Keep task text explicitly sized to its available column and shape ellipsized lines only after final layout. GPUI 0.2.2 can retain shortened glyph runs across intrinsic-width measurements; correct box bounds alone do not establish complete native text. Align the task form with its heading and group record date controls next to the date.
- Run `scripts/check.sh` before delivery. GPUI TestPlatform checks establish layout bounds and dispatched events only; they do not render native pixels or verify IME composition. UI acceptance needs the actual native app; compilation and headless tests are not visual or cross-platform acceptance.
- Native input acceptance must include ordinary key presses, editing and shortcuts, plus typing immediately after dismissing native save/confirmation dialogs and reopening the management window. A visible caret or successful paste alone does not prove keyboard input works. After changing macOS window styles, preserve GPUI's native text-input responder; defer handle-based window access from global keyboard callbacks until the dispatching window's borrow ends.
- IME acceptance requires actual composition and candidate confirmation through a real input method, including Return, cancellation, dialog return and restart. Synthetic ASCII key events and pasted Chinese are insufficient. Preserve the pre-GPUI AppKit initialization in `platform::prepare_application`; see `docs/plans/macos-ime-startup.md`.
- Name branches `feat/...`, `fix/...` or `docs/...`. A substantial rewrite needs explicit approval before merging main. Do not publish a release without a release instruction.
- Do not commit credentials, private data, local paths, installers or build outputs. Keep documentation concise and about current behavior.
- Remove task-created temporary artifacts after verification. Preserve source, active app artifacts, useful build caches and concise verification evidence.
